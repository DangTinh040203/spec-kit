# Research: Todo Backend API

**Feature**: `001-todo-backend-api` | **Date**: 2026-11-26 (re-planned) | **Plan**: [plan.md](./plan.md)

Re-planned for the stack the user chose:

1. Turborepo monorepo with two apps, frontend and backend
2. Frontend: Next.js + Tailwind CSS + shadcn/ui + Framer Motion (animation where useful)
3. Backend: NestJS + Prisma + PostgreSQL + Redis

Feature 001 is backend only (spec: "No user interface in this phase"). It sets up the monorepo
and builds `apps/api`. The frontend app `apps/web` is created by feature 002; its stack is
recorded here (R13) so the monorepo is designed for it from the start.

Each entry gives a decision, why it was chosen, and what else was considered. Nothing in the
Technical Context is left as NEEDS CLARIFICATION.

## R1. Monorepo: Turborepo + pnpm workspaces

- **Decision**: Turborepo at the repository root with pnpm workspaces:
  - `apps/api`: NestJS backend (this feature)
  - `apps/web`: Next.js frontend (feature 002, not created here)
  - `packages/`: empty for now; shared packages are added only when a second app needs them
- Root `turbo.json` defines `build`, `dev`, `typecheck`, and Prisma `db:generate` tasks, with
  `build` depending on `^build` and `db:generate` so the Prisma client exists before the API
  compiles.
- **Rationale**: Chosen by the user. One install, one task runner, cached builds, and
  `pnpm --filter api …` to work on a single app.
- **Alternatives considered**: Separate `backend/` and `frontend/` folders without a monorepo
  tool (the previous plan; no shared task pipeline); Nx (heavier, more config).
- **Deferred**: A shared `packages/api-types` (request/response types for the frontend) is
  decided in feature 002, when there is a consumer. Creating it now would be unused code.

## R2. Runtime, language, and package manager

- **Decision**: Node.js 22 LTS or later (local machine has v26), TypeScript strict mode, pnpm
  (installed, v12). Root `package.json` sets `"packageManager"` so Turborepo and pnpm agree.
- **Rationale**: Turborepo works best with a declared package manager; pnpm workspaces are its
  most common pairing. Next.js and NestJS both support this Node range.
- **Alternatives considered**: npm or Yarn workspaces (slower installs, no gain here).

## R3. API app scaffolding: manual and minimal

- **Decision**: Create `apps/api` by hand with only the packages in R10, not with `nest new`.
- **Rationale**: `nest new` adds Jest, ESLint, Prettier, and a sample app. Tests are not required
  by the constitution and every package needs approval (Principle IV).
- **Alternatives considered**: `nest new` then delete extras (installs unapproved packages first).

## R4. PostgreSQL and Redis in Docker

- **Decision**: One root `docker-compose.yml` with PostgreSQL 17 and Redis 7 (or 8), for local
  development only. Connection strings come from `apps/api/.env` (`DATABASE_URL`,
  `REDIS_URL`), loaded with Node's built-in `--env-file`.
- **Rationale**: Both services start with one command; Docker is already installed. Built-in env
  loading avoids `@nestjs/config` for two variables.
- **Alternatives considered**: Installing PostgreSQL and Redis on the host (harder to reset);
  `@nestjs/config` (extra dependency).

## R5. Prisma setup in the monorepo

- **Decision**: Prisma ORM, latest stable major at install time, schema at
  `apps/api/prisma/schema.prisma` (the constitution's `prisma/schema.prisma`, relative to the
  backend app). The generated client is output inside `apps/api` and imported only from
  `infrastructure/`. If the installed major requires a driver adapter (Prisma 7 does), use the
  official PostgreSQL adapter (`@prisma/adapter-pg` + `pg`). The exact generator and config file
  layout is confirmed against Prisma's docs at install time.
- **Rationale**: Keeping Prisma inside `apps/api` means the frontend can never import it, which
  enforces Principle I at the package level too.
- **Alternatives considered**: A shared `packages/database` (useful only if a second backend
  needs the same database; not the case).

## R6. Identifiers

- **Decision**: UUID v4 generated by PostgreSQL (`@default(uuid())`, `@db.Uuid`). The use case
  checks the id format first and answers a malformed id with "not found" (FR-021) without
  touching the cache or database.
- **Rationale**: Not guessable, no extra library, and the check stops PostgreSQL's "invalid uuid"
  error from becoming a 500.
- **Alternatives considered**: Auto-increment integers (guessable, leak counts); cuid/nanoid
  (extra dependency).

## R7. Ordering: dense integer positions per status

- **Decision**: `position` is an integer, 0 = top, dense (0, 1, 2, … with no gaps) within each
  status. Each change runs in one database transaction:
  - create at top: `position = position + 1` in the target status, insert at 0;
  - move: close the gap in the source status, clamp the target index to the end, open a gap in
    the target status, write status + position;
  - delete: remove, then `position = position - 1` for rows below it;
  - status change: a move to index 0 of the new status (FR-011).
- **Rationale**: Meets FR-024–FR-027 directly. Each shift is one
  `UPDATE … WHERE status = ? AND position >= ?`, fast at 10,000 todos.
- **Alternatives considered**: Fractional / LexoRank keys (client would not see 0..n-1, needs
  rebalancing); linked list (slow ordered reads, hard to page).
- **Constraint note**: No unique index on `(status, position)`, because shifting rows would
  briefly create duplicates and Prisma cannot declare deferrable constraints. A plain index keeps
  reads fast. Concurrent writers are out of scope (single user, last move wins).

## R8. Validation and error format

- **Decision**:
  - Request shape is validated in the presentation layer with `class-validator` +
    `class-transformer` through a global `ValidationPipe` (`whitelist`,
    `forbidNonWhitelisted`, `transform`) whose `exceptionFactory` collects every failing field
    into one error (FR-020).
  - Title length is counted in grapheme clusters with the built-in `Intl.Segmenter` through a
    custom validator, so Vietnamese text counts as a person reads it. Titles are trimmed first.
  - Due dates must match `YYYY-MM-DD` and be a real calendar date (`IsISO8601` strict).
  - The domain entity re-checks its own invariants so a use case can never create an invalid
    todo.
  - One global exception filter turns domain errors, validation errors, malformed bodies, and
    unexpected errors into `{ "error": { "code", "message", "details": [{ "field", "reason" }] } }`
    (FR-019, FR-022).
- **Rationale**: Standard NestJS approach; all problems in one response; no internal details
  leak.
- **Alternatives considered**: Zod (second validation style, extra dependency); domain-only
  validation (one error at a time, HTTP concerns in the domain).

## R9. Timestamps and dates

- **Decision**: `createdAt` (`@default(now())`) and `updatedAt` (`@updatedAt`) as `timestamptz`,
  returned as ISO 8601 UTC. `dueDate` is PostgreSQL `date`; the domain keeps it as a
  `YYYY-MM-DD` string and the mapper converts in UTC. A status request with the current status
  writes nothing, so `updatedAt` does not move.
- **Rationale**: Avoids time-zone shifts on date-only values.
- **Alternatives considered**: Domain-managed timestamps with an injected clock (more code, no
  benefit without tests).

## R11. File-name roles and rules that the constitution does not allow yet

The design needs these, and Principle III says a new suffix MUST be added to the table before
first use:

| Needed | Layer | Example | Constitution today |
| --- | --- | --- | --- |
| `.error.ts` | domain | `todo-not-found.error.ts` | Not in the table |
| `.filter.ts` | presentation | `http-exception.filter.ts` | Not in the table |
| `.validator.ts` | presentation | `grapheme-length.validator.ts` | Not in the table |
| `redis.service.ts` | shared infrastructure | Redis client wrapper | `.service.ts` is reserved for `prisma.service.ts` only |
| `cached-todo.repository.ts` | infrastructure | Redis cache decorator around the Prisma repository | Repository implementations MUST use the `prisma-` prefix; Principle I describes infrastructure as Prisma-based only |

- **Decision**: Amend the constitution (MINOR → v2.2.0) before implementation: add the three
  suffixes; allow `.service.ts` for infrastructure client wrappers (`prisma.service.ts`,
  `redis.service.ts`); allow a `cached-` prefix for repository decorators that add caching;
  state that infrastructure may use Redis for caching. `main.ts` stays the standard NestJS
  entry point with no role suffix.
- **Alternatives considered**: Hiding errors in the entity file and the validator in a DTO file
  (mixes roles); naming the cache decorator `prisma-…` (misleading).

## R12. Redis: read cache with version-key invalidation

The spec has no requirement that needs Redis; PostgreSQL alone meets SC-003. Redis is used
because the user chose it, in the role where it fits this API best and cannot change behavior.

- **Decision**: Cache-aside for reads, through `CachedTodoRepository`, a Decorator around
  `PrismaTodoRepository` that implements the same `TodoRepository` contract:
  - `findById(id)` → key `todo:v{n}:{id}`; `findPage(query)` → key
    `todos:v{n}:{status}:{sort}:{order}:{page}:{pageSize}`; TTL 60 seconds.
  - Every write (create, update, status change, move, delete) runs against PostgreSQL first and,
    after it commits, increments the version counter `todos:version` (`INCR`). All old keys are
    then unreachable and expire on their own. One counter is used because a move or create
    changes the positions of other todos, so a single write can affect many cached entries.
  - If Redis is down or slow (short command timeout), the decorator logs a warning and calls the
    Prisma repository directly. The API keeps working and returns correct data (FR-022 still
    applies only to real failures).
  - `todo.module.ts` binds `TodoRepository` to `CachedTodoRepository`, which receives
    `PrismaTodoRepository` and `RedisService`. Use cases do not know the cache exists.
- **Rationale**: Clean Architecture keeps caching an infrastructure detail (Open/Closed: no use
  case changes). Version-key invalidation is simple and never serves stale data after a write
  from this API, which matters for SC-004 (paging returns each todo exactly once) and for the
  board's "order stays after reload" rule in 002.
- **Alternatives considered**:
  - `@nestjs/cache-manager` interceptors on controllers (caches in the presentation layer; hard to
    invalidate list pages correctly; extra dependency).
  - Deleting matching keys with `SCAN` on each write (slower, more code than a version counter).
  - Redis for rate limiting or locks (no requirement for either; single user).
  - No Redis in 001, added later (rejected: the user asked for it in the stack).
- **Note for review**: If you meant Redis for something else (for example, queues or real-time
  updates in feature 002), say so and this entry changes. The cache can also be switched off by
  binding `TodoRepository` straight to `PrismaTodoRepository`.

## R13. Frontend stack (recorded for feature 002, not built here)

- **Decision**: `apps/web` with Next.js (App Router, TypeScript), Tailwind CSS, shadcn/ui
  (components copied into the app, built on Radix), and Framer Motion for animation where it
  helps (card moves on the board). Framer Motion is now published as `motion`
  (`import { motion } from "motion/react"`); feature 002 confirms the package name at install.
- **Ports**: `apps/web` on 3000 (Next.js default), `apps/api` on 4000.
- **What 001 does for it**: the API enables CORS for the origin in `CORS_ORIGIN`
  (default `http://localhost:3000`), and its JSON contract ([contracts/openapi.yaml](./contracts/openapi.yaml))
  is the interface the frontend will call.
- **Left to feature 002**: drag-and-drop library, data fetching approach, shared API types
  package, and frontend file-naming rules for the constitution.
